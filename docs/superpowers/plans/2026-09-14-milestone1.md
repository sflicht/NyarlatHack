# NyarlatHack Milestone 1 Implementation Plan

> **For agentic workers:** Use subagent-driven-development or executing-plans to implement this plan task-by-task. Use test-driven-development: record failing tests before implementation and rerun them afterward.

**Goal:** Ship the Tier 2 director described in README.md, including actual bounded gameplay mutations, not merely an event logger.

**Architecture:** dNetHack remains authoritative. Player-observable events feed a separate Python director; a strict, bounded mailbox transports mutation proposals into safe-point validation. Seeded gameplay and accepted application schedules can be replayed without a model. Runtime code generation is excluded.

**Tech Stack:** Existing C engine and GNUmakefile, Python 3.11+ standard library where practical, uv for Python environments, terminal-driven gameplay tests.

**Spec:** README.md Milestone 1; AGENTS.md. User approved implementation in Discord on 2026-09-14. Detailed choices below refine that design, not authorize Tier 3.

## Global constraints

- Read AGENTS.md. Do not edit protected instruction files without approval.
- No Tier 3, Lua, source rewriting, public deployment, or code in bones files.
- Keep upstream hooks small. Preserve licenses. Do not regenerate macromagic.h unnecessarily.
- New code lives primarily in src/chaos_*.c, include/chaos*.h, chaos/, tests/chaos/, and docs/.
- The illustrative mutation names in README.md are examples, not a requirement to implement every possible category. Ship a small documented registry with at least two genuine rule-changing effects plus ambient messages; all exposed entries must work and have tests.
- No model spending is authorized by this milestone. Provide a configured model backend, test it against an explicitly labeled local protocol fixture, and distinguish that from live-model validation. Offline backends must work without keys or network.
- A seed and whisper text alone are not enough for replay. Record player inputs, exact application points, initial options/identity, engine version and relevant environmental conditions. State actual replay guarantees and limitations.
- Treat all mailbox and model output as untrusted data. No evaluation, shell commands, arbitrary files, pointers, or unconstrained setters.
- Validate static schema/bounds at ingestion AND dynamic eligibility at application. If a telegraph errors or admission logging fails, do not silently apply a mutation.
- No-whisper observation must not consume random draws or reveal unidentified items/hidden monsters to the director.
- Unit tests alone do not prove gameplay replay. Build and exercise real game processes; a passing scoreboard query is not a play test.
- Preserve the initial binary/data at /home/hermes/.local/share/nyarlathack/baselines/ff37b3a7a. Git base is ff37b3a7a.

## Task 1: Engine contract and executable validation

**Files:** include/chaos.h, src/chaos_protocol.c, tests/chaos/test_protocol.py, docs/chaos-protocol.md.
**Interfaces:** A versioned event envelope, a finite mutation registry, a documented bounded request envelope, explicit acknowledgement/rejection records. The protocol document must fix every field, type, bound, cost, lifetime, identifier rule and scheduling rule before the sidecar is implemented.

- [ ] Write parser/validator tests before production code. Require valid requests to parse and reject: missing telegraph, unknown mutation/key, duplicate fields, booleans as integers, numeric overflow/fraction, oversized records, embedded NUL/control characters, malformed/trailing JSON, stale/duplicate identifiers, excessive cost and excessive duration.
- [ ] Run `python3 -m unittest discover -s tests/chaos -p 'test_*.py' -v` and preserve actual failing output outside tracked source.
- [ ] Implement bounded C validation with no dynamic interpretation. Reuse a small properly licensed parser if justified; do not use substring matching as JSON parsing.
- [ ] Define costs in the engine registry, never trust model-supplied cost. Define how active mutations expire and budget is reserved/released so repeated requests cannot stack past the cap.
- [ ] Rerun the focused suite; record exact results, not invented expected output. Commit task with a conventional subject.

## Task 2: Engine observation and real mutation effects

**Files:** src/chaos_engine.c, include/chaos.h, GNUmakefile, minimal hooks in existing engine files found by source inspection, tests/chaos/.
**Interfaces:** Disabled-build no-op hooks; runtime activation by explicitly configured run directory; event and mailbox filenames documented in docs/chaos-protocol.md. Observation, effects, and transport must be separable for tests.

- [ ] Add failing tests for event escaping/redaction, safe-point admission, telegraph-before-effect, no-change behavior with empty mailbox, expiry, budget and duplicate handling.
- [ ] Implement CHAOS build toggle, default compiled on but opt-in run I/O. Prevent stale objects when switching the build flag.
- [ ] Emit events for kill, eat, read, zap, apply, prayer, level enter/leave, Sanity/Insight changes and death. Distinguish attempts from completed actions in event names or data. Never reveal hidden item type or unobserved killer identity.
- [ ] Poll at safe points for level changes, prayer, sleep, and Sanity thresholds. Nested mutation callbacks must not reenter admission. Apply at most a bounded number per safe point.
- [ ] Implement small registry: favor ward efficacy, spawn weighting and ambient effects if source inspection supports them cleanly. If a different pair of genuine rule changes is safer, document the choice. No fake implementation consisting only of a log message.
- [ ] Persist admitted mutations, lifetime, budget, deduplication and application counters across save/restore. Keep state out of bones. Ensure disabled CHAOS builds do not silently reinterpret incompatible saves.
- [ ] Build `make -j4 install` and inspect exit code and diagnostics. Test CHAOS-off from a clean independent build as well.
- [ ] Commit engine hooks and tests after passing focused checks.
